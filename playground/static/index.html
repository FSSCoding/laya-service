The human CLI is .venv/bin/laya — laya health, laya choice --state … --questions …. Agent MCP tools (laya_system_one etc.) exist too but this page only talks to /api/query and /api/health.

Separate HTTP requests are NOT coalesced. The 5 ms request-batcher window does not merge distinct browser submissions into one inference pass — RequestBatcher._process_batch() processes queued payloads serially. Do not raise HTTP concurrency expecting throughput. Several questions inside one /system_one request, however, are answered in one model forward pass — that is what the Batch tab means. See benchmarks/HARDENING-REPORT.md §3 and src/laya_server/batcher.py.

State

Sent to the model as a JSON string exactly as typed. Laya sees the state as input content — not as an instruction to generate text.

What question does this answer? “Which option is most likely for this state?”

Options — a key identifies the option in the answer; an optional description adds context but spends tokens.

Practical initial experiments: 2–32 options. More options and longer descriptions consume the 192-token head budget; tested 128 short options returned HTTP 500. There is no universal safe option count independent of text lengths — benchmarks/HARDENING-REPORT.md §2.1.

What question does this answer? “On your ordered rubric, where does this state land?”

Ordered level rows, lowest first. Guided mode suggests 2–10 levels.

Index 0 = lowest. The score is a probability-weighted mean over 0…N−1 — not a 0–1 probability and not a calibrated urgency scale.

Hardening probes found non-monotonic ordinal results — do not recommend score as a reliable priority ranking. A one-level rubric caused a 500 crash, and 11 levels were accepted despite the documented 2–10 range (kept available in the break-it lab, with a warning — not endorsement). benchmarks/HARDENING-REPORT.md §2.2.

What question does this answer? “Is this proposition true given the state?”

True / false descriptions (optional — learn how criteria affect the answer)
Hardening probes found negation blindness and factual mismatches: a high probability is not proof the statement is true. benchmarks/HARDENING-REPORT.md §2.3.

What question does this answer? “Several typed questions about the same state, in one forward pass.”

Batch ≠ simultaneous HTTP requests. One POST carries a questions map of every ID → spec; the service answers all of them in one model forward pass. That is not cross-request coalescing. Distinct HTTP requests remain serial at the worker today. See the warning above the form and benchmarks/HARDENING-REPORT.md §3.

usage.input_tokens aggregates rendered tokens across each question’s sequence — it is not a single 512-token pool for the whole multi-question request.

Multi-select (composition, not a fourth primitive)

Compose one noul question per candidate inside one batch request; compare all P(true) values. Do not imply a native multi-select type — the model only knows choice / score / noul.

Try: turn your support-triage state into a batch with c1–c3 noul questions “Applies: billing” / “Applies: account” / “Applies: technical”, and compare against a single choice on the same state.

Refs: src/laya_server/primitives.py (multi_select), README.md §Python primitives.

Ranking (with a shared rubric — and a caveat)

Score each candidate against one shared ordered rubric as separate score questions in one request. But the hardening probes measured score non-monotonicity, so rankings need independent evaluation before you trust them.

Try: rank three candidate fixes with a shared 5-level rubric; then re-run each as its own request and check the distribution shape doesn’t reorder them.

Refs: src/laya_server/primitives.py (rank), benchmarks/HARDENING-REPORT.md §2.2b.

Inversion (same decision, different framing)

Ask the same decision as one choice question and as several binary noul questions. Differences between framings are observations, not an accuracy verdict — that would need the deferred semantic corpus.

Try: your triage state as one choice (billing/account/technical) plus three noul propositions, one per category; note where the modes disagree.

Ref: benchmarks/FUTURE-METHODS.md (deferred research).

Many questions vs many requests

One request with many questions is one forward pass. Multiple HTTP requests are processed serially at the worker today — the batcher’s 5 ms window does not merge them into one GPU call.

Try: put all three of your questions in the Batch tab and run once; then note that submitting them as three separate runs does not share a pass.

Refs: src/laya_server/worker.py, src/laya_server/batcher.py, benchmarks/HARDENING-REPORT.md §3.

Token budgets and silent truncation

The ~512-token limit applies per rendered question sequence (type, instructions, option/level head, state); the head has its own ~192-token budget. usage.input_tokens is measured after any truncation and does not prove the original state fitted. The page cannot compute the exact tokenizer count — so there is no fake remaining-token meter or automatic “truncated” flag.

Try: the Huge state probe — the decisive fact sits near the end; see whether the model still uses it.

Refs: src/laya_server/sequence.py, benchmarks/HARDENING-REPORT.md §4.

What has actually been tested

Safe operating envelope, scaling curves, cache/latency behaviour, and 8 identified bugs/issues — plus the deferred adoption-evaluation methodology. Prior docs sometimes describe coalescing as functional; the measured behaviour is in the hardening report.

Try: read the safe-operating-envelope table before pushing your probe further.
